# 实现、检查与局部迭代

## 依赖与工程

使用当前可用的 HyperFrames 官方技能与文档理解工程契约。本 Skill 负责事实、镜头与默认风格。新环境确认 Node.js、Chrome、FFmpeg／FFprobe 与项目的 CLI 版本；具体要求以当前已安装版本及 --help 为准。不要为本次更新修改无关模型或账户配置。

每个产品保存事实、分镜、主题令牌、时间线、工程、media/、renders/ 与质量记录。style-preset.json 是可编辑的设计基线，不是 HyperFrames 原生 schema。分镜与品牌为数据，镜头可复用；素材、字体和图标在渲染前落地并保存许可。

## 新工程与现有工程

新产品／新组件先验证一个代表性短段，覆盖实际字体、章节与真实 UI。通过结构／浏览器检查、静帧与真实编码验证后扩展。

现有工程的小修改直接修改相关场景，不重复完整采访或重建整片。保持已认可的片长、语言、镜头与数据，除非当前用户要求改变。使用项目历史保留原版。英文切换遵循 style-and-shots.md 的全内容与坐标检查。

## 检查与渲染

在工程目录执行当前版本支持的命令，例如：

```sh
npx hyperframes check --json
npx hyperframes snapshot --at 2,6,10
npx hyperframes render --quality delivery --output renders/final.mp4
ffprobe -v error -show_format -show_streams renders/final.mp4
```

check 已包含 lint；不要重复相同检查而没有新变化。保留关键画面与输出验证。结构通过不代表版式／听感通过，不能只交 HTML 预览就声称 MP4 成功。

正常渲染失败时先读取实际失败阶段。浏览器或编码超时可以降低到 1–2 个 worker；若当前版本支持，可尝试一次分段编码。不要只反复延长超时并从头重跑。若改用逐帧缓存后独立编码，必须保留实际项目的 seek、媒体同步与字体契约，不能将 Mole 的无视频单根时间线逻辑套到任意项目。

用户要求直接交付时完成本地导出；用户要求先审片时给真实预览。上传、公开发布和付费生成遵守当前授权，不增加无必要的确认。

## 只修改配乐

画面已认可、修改仅涉及音乐时：

1. 将完整新音轨编辑并输出到本地，保留音乐许可与编辑记录。
2. 测量最终文件的响度和峰值，核对揭晓点与片尾；更新工程所引用的音轨。
3. 用随附 replace_soundtrack.py 复用原片的视频流、替换音轨。
4. 核对输出尺寸、帧率、时长、画面流 SHA-256 与完整解码；保存返回的检查 JSON。

```sh
python3 scripts/replace_soundtrack.py old.mp4 new-score.m4a new.mp4 --ffmpeg /path/to/ffmpeg --ffprobe /path/to/ffprobe
```

脚本输入应是已经完成的配乐，不负责选曲、剪乐句或自动卡点。要求音轨覆盖画面；短音轨应先在编辑阶段完成尾音／留白方案。默认拒绝覆盖已有输出，明确需要替换时用 --overwrite。

## 验收范围

视觉修改核对相关标题、UI 焦点、裁切与转场，再验证最终编码。音乐修改保留实际响度与峰值测量、画面一致性和全片解码。无法实际听取／观看时说明已完成的检查，不编造试听或看完整片的经历。

Skill 的 verified-workflow.md 只记录真实跑通的范围。第二个产品复用时观察是否只需替换数据与品牌；如果需要重写多数组件，先改善接口再扩展风格库。

## 模拟点击与最终编码裁切

用户明确要求时，指针、按钮反馈和接触环置于同一个 UI camera 内，使用确定性局部时间线；镜头稳定后再瞄准点击，退场后再切镜头。模拟点击与示例数据明确标注，不声称真实录屏或执行成功。默认不加入虚拟点击声。

在本地 macOS 案例中，普通桌面 Chrome 渲染曾裁掉底部约 87 像素，而结构检查与静帧看似正常。改用 CLI 管理的 chrome-headless-shell 后编码正常。此经验不证明所有 Chrome 都有相同问题；新环境显式检查最终 MP4 的底边、按钮和注释。用实际编码帧验收，不能只依靠 Studio 预览。

同时改配乐与片长时，需要重新渲染画面；仅替换音轨的压缩流复用脚本不适用。新时间线的章节、镜头、点击、字幕、音轨与根时长必须同步更新。
